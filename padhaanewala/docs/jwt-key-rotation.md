# JWT signing key rotation (H-07)

## Scope and constraints

This procedure covers the two HMAC signing slots used by the backend:

| Slot | Used for | Setting |
|------|----------|---------|
| Access | `create_access_token()` — every bearer token | `JWT_SECRET_KEY` |
| Refresh | `create_refresh_token()` — the cookie/body token accepted by `/auth/refresh` and `/auth/logout` | `JWT_REFRESH_SECRET_KEY` |
| Retired access | verification only, during a grace window | `JWT_PREVIOUS_SECRET_KEY` |
| Retired refresh | verification only, during a grace window | `JWT_PREVIOUS_REFRESH_SECRET_KEY` |

Rules that must not be broken:

- The algorithm stays `HS256` (or another configured HMAC algorithm). Rotation changes key material, not the algorithm or token shape.
- Access and refresh keys are **independent** CSPRNG draws. Never reuse one value in two slots, including across a rotation.
- Staging and production refuse to boot if a key is empty, a placeholder, too short, low-entropy, a known development value, or shared with another slot. Development is intentionally permissive so local tests keep working.
- A retired key is accepted for **verification only**. Signing always uses the current key, so a compromised or retired key cannot mint a new token.
- Refresh-token ledger rows (`refresh_tokens`) are untouched by rotation. Rotation detection, family revocation on reuse, logout revocation and `MAX_ACTIVE_REFRESH_TOKENS` continue to work on tokens signed with either the current or retired refresh key.
- **No production credential is changed by this repository change.** The values in the secret manager stay as they are until an approved rotation plan is executed. Do not deploy to production as part of this change.

## Generating keys without leaking them

Generate each value directly into the destination secret store. Do not paste generated values into tracked files, chat, tickets, CI output or shell history. Do not echo them back to a terminal or log.

```sh
# One call per slot, each an independent 256-bit draw.
openssl rand -hex 32    # new access key
openssl rand -hex 32    # new refresh key
```

The application also exposes `app.utils.security.generate_signing_key()` for rotation tooling and tests. It returns a key; it never prints or logs it.

## Planned rotation (no known compromise)

1. **Prepare.** Generate two new keys into the secret manager. Confirm they differ from each other and from every current and previously used value.
2. **Stage the grace deployment.** Set:
   - `JWT_SECRET_KEY` = new access key
   - `JWT_REFRESH_SECRET_KEY` = new refresh key
   - `JWT_PREVIOUS_SECRET_KEY` = old access key
   - `JWT_PREVIOUS_REFRESH_SECRET_KEY` = old refresh key
3. **Deploy** to staging first. Confirm login, refresh, logout and a protected-page request succeed. Confirm a token minted before the deployment still works (that is the purpose of the retired slots).
4. **Observed grace period.** Keep the retired slots set for longer than the longest outstanding token you intend to honour. Recommended: at least `JWT_ACCESS_TOKEN_EXPIRE_MINUTES` plus one refresh cycle (default 30 min + 25 min ≈ 1 hour); longer if you deliberately support long-lived sessions.
5. **Close the window.** Clear `JWT_PREVIOUS_SECRET_KEY` and `JWT_PREVIOUS_REFRESH_SECRET_KEY` in the secret manager and redeploy. From this point tokens signed with the old keys are rejected, and any still-valid old refresh token can no longer be exchanged for a new session.
6. **Verify closure.** Run the old-key rejection tests (see below) against the deployed configuration using a deliberately retired test key, never a production value.

## Emergency rotation (key compromise suspected)

If a signing key may have been disclosed, **do not use a grace window**:

1. Set both current keys to fresh independent values and leave both previous slots empty.
2. Deploy immediately — every existing access and refresh token becomes invalid at once and all users must sign in again.
3. Invalidate server-side state as an extra safeguard if session ledger rows from the compromised period may have been accessed: revoke affected refresh-token families via `app.services.session_service.revoke_family()`.
4. Follow `docs/breach-response-playbook.md` for notification and log review.

Emergency rotation is disruptive but is the only option that guarantees a disclosed key cannot be used.

## Validation

Run against the backend environment with the production-shaped configuration:

```sh
python -m pytest tests/test_jwt_key_hardening.py -q
python -m pytest tests/test_auth.py tests/test_session_security.py tests/test_rbac_rules.py -q
```

The hardening suite asserts:

- known development keys, placeholders, short keys and shared keys are rejected in staging and production;
- access and refresh keys generated by `generate_signing_key()` are independent;
- a token signed with a retired key verifies while the retired slot is populated and is rejected after it is cleared;
- a token signed with an unrelated old key is rejected even while a different retired key is configured;
- login, logout, refresh, expiry, invalid-signature and refresh-reuse-detection behaviour is unchanged.

## Operational reminders

- Render injects `JWT_SECRET_KEY` / `JWT_REFRESH_SECRET_KEY` with `sync: false`; rotation variables must be added there as secret values too, never in `render.yaml`.
- Docker Compose production reads `${JWT_SECRET_KEY:?...}` / `${JWT_REFRESH_SECRET_KEY:?...}` from the deployment environment. Add the retired slots there for the duration of the grace window.
- Logs and build artefacts must never contain key material. The known-development-key denylist stores only SHA-256 fingerprints; validation errors report the reason, not the value.
