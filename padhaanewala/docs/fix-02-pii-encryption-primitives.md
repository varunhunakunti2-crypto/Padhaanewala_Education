# Fix 02 T1 — PII encryption primitive specification

**Status:** Implemented as isolated primitives only. No database, route, OTP,
authentication, search, migration, environment, deployment or frontend change is
part of T1.

**Relationship to ADR-0009:** ADR-0009 remains in force for integrated
field-level encryption. Its Decision 2 is not silently reversed here: this
change adds a reusable, independently testable primitive and a design record.
Production storage integration stays blocked until the D-01 supersession
decision in `fix-02-pii-encryption-final-plan-revision.md` is approved.

---

## 1. Envelope format

### 1.1 Stored representation

```text
pe1.<base64url-no-padding(BODY)>
```

- `pe1` is the **envelope format version** (`ENVELOPE_FORMAT_VERSION = 1`).
- The base64url alphabet is exactly `A-Z a-z 0-9 - _`.
- Padding (`=`), whitespace, line breaks, standard base64 `+`/`/`, and any
  other characters are rejected.
- Decoding is canonical: the decoded bytes must re-encode to the exact supplied
  string.

### 1.2 Binary body

```text
byte 0      envelope format marker, always 0x01
byte 1      encryption key version, 1..255
bytes 2-13  96-bit random nonce
bytes 14..  AES-256-GCM ciphertext with the 128-bit tag appended
```

The format marker is not a key version. The key version is byte 1. This makes
the two concerns explicit:

| Concern | Where it lives | Changes when |
|---|---|---|
| Envelope format version | `pe1.` prefix and byte 0 marker | Serialization layout changes |
| Encryption key version | byte 1 | A key is rotated |

This refines the plan's shorthand layout by adding a dedicated key-version byte
while retaining the `pe1.` prefix and the `0x01` marker. It is documented here
rather than changed silently.

### 1.3 Nonce and tag

- Nonce: exactly 12 bytes, generated by `secrets.token_bytes(12)` for every
  `encrypt_text` call.
- Tag: AES-GCM's 128-bit (16-byte) tag, appended to the ciphertext by
  `cryptography`'s `AESGCM`.
- Repeated encryption of the same plaintext produces different envelopes.

## 2. AAD specification

Canonical AAD string:

```text
padhaanewala|pii-aad|v1|{table}|{column}|{pii_context_id}|{purpose}
```

Encoded as UTF-8 before being passed to AES-GCM.

### 2.1 Component rules

| Component | Rule |
|---|---|
| `table` | lower snake_case, 1-64 chars, no `|` |
| `column` | lower snake_case, 1-64 chars, no `|` |
| `pii_context_id` | canonical lowercase UUIDv4 string, or `uuid.UUID` with version 4 |
| `purpose` | one value from the fixed allowlist below |

Because `|` is forbidden inside every component, the delimiter cannot be
confused with component content. Non-canonical UUIDs, non-v4 UUIDs, unknown
purposes and delimiter injection are rejected before encryption.

### 2.2 Fixed purpose allowlist

```text
user_identity
student_profile
admin_staff
counsellor_staff
enquiry
lead_note
guardian_consent
otp
consent_record
data_request
audit_ip
refresh_token_ip
college_submission
```

Arbitrary caller-supplied purposes are not accepted.

### 2.3 Context lifecycle expectation

`pii_context_id` is generated once per row as UUIDv4 and remains immutable for
the life of the row. Moving a ciphertext to another row, table, column or
purpose changes the AAD and makes authentication fail.

## 3. Key-version configuration contract

### 3.1 Key material

- AES-256 requires exactly 32 raw bytes.
- Hex strings are accepted only as exactly 64 hex characters.
- Placeholder strings are rejected in every environment.
- Low-variety byte strings are rejected.
- Key material is redacted from `repr()` and never included in an exception
  message.

### 3.2 Keyring

`PIIKeyring` holds:

- one `current` key used exclusively for writes;
- zero or more `previous` keys used only for reads;
- an explicit `environment` value (`development`, `staging`, `production`).

Version rules:

- versions are integers `1..255`;
- current and previous versions must be unique;
- an unknown version fails closed;
- a wrong key at a configured version fails AES-GCM authentication;
- no key is read from process environment, `.env` files, source or request data
  by this T1 module.

### 3.3 Production expectation

The module requires callers to choose keys deliberately. A deployed integration
must source both current and previous PII encryption keys from the approved
secret manager and pass them to `PIIKeyring`. Production must never use a
placeholder or hardcoded development key. No production key value is created,
printed or stored by T1.

---

## 4. Rotation expectation

1. Deploy a new key as `current` with the old key retained in `previous`.
2. New writes use the new version; reads accept both versions.
3. Re-encrypt and verify stored values in a separately approved migration or
   job.
4. Retire the previous key only after verification and backup/restore evidence
   exist.

T1 does not rotate any key, does not change environment configuration and does
not create HMAC lookup tokens.

---

## 5. Failure behaviour

The primitive raises narrow exceptions without sensitive detail:

- `InvalidContextError` — invalid table, column, purpose or context.
- `InvalidKeyError` — invalid key material, version or configuration.
- `InvalidEnvelopeError` — malformed, non-canonical or unsupported envelope.
- `UnknownKeyVersionError` — version byte is not configured.
- `DecryptionError` — authentication failed or plaintext was not valid UTF-8.

No logging is performed in this module.

---

## 6. Security limitations and unresolved decisions

- Randomized AES-GCM gives no equality search. HMAC lookup tokens remain a
  separate, not-yet-approved work item.
- AAD binding protects against cross-row, cross-table, cross-column and
  cross-purpose substitution, but the application must supply the correct
  immutable context from its own trusted data.
- Key custody, secret-manager names, production rotation windows and encrypted
  column schema remain unresolved owner decisions.
- No migration, backfill, dual-write or plaintext removal is authorised by T1.
